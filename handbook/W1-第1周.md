## D1 · 写一个会「说话」的服务

> **📍 在哪做**
> - **环境**：虚拟机（Windows 终端里 `ssh shawny@192.168.223.129` 进去）
> - **目录**：`~/aiops`
> - **新建**：`app.py`
> - **终端**：2 个（一个跑服务、一个 curl 验证）

### 今天的目标

写一个 30 行的 Python 服务，访问它能返回内容，访问 `/metrics` 能返回一堆数字。

### 为什么做这一步

监控系统需要有个**被监控的对象**。真实公司里这是业务服务；你自己写一个，好处是：

- 你想让它变慢它就变慢，想让它报错它就报错——**可以随意制造故障**
- 你知道它每一行代码，出问题不会一头雾水

这就是你的「实验小白鼠」。

### 用到的工具

| 工具 | 是什么 | 为什么是它 |
|---|---|---|
| **Python** | 编程语言 | 运维和 AI 都用它 |
| **FastAPI** | Web 框架 | 20 行起一个服务，语法简单 |
| **uvicorn** | 应用服务器 | FastAPI 写的代码要靠它变成真正的端口 |
| **prometheus-client** | Python 库 | 帮你在 `/metrics` 上吐标准格式的数字 |

**关键概念：HTTP 服务怎么工作**

```
你的程序监听 8000 端口 → 浏览器/curl 发请求 "GET /" → 程序返回 {"msg":"ok"}
```

`/metrics` 只是一个特殊路径，返回的不是给人看的网页，而是一段**固定格式的纯文本数字**——Prometheus 只认这个格式。

```python
# app.py —— 一个会暴露指标的小服务
import time
import random

from fastapi import FastAPI
from fastapi.responses import Response, JSONResponse
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST

app = FastAPI(title="aiops-demo")

# ── 两个指标 ────────────────────────────────────────────
# Counter：只增不减的计数器。这里按「路径」和「状态码」分组统计请求数
REQUESTS = Counter("app_requests_total", "请求总数", ["path", "status"])

# Histogram：直方图。记录每次请求耗时，用来算 P95（95% 的请求快于多少毫秒）
LATENCY = Histogram(
    "app_latency_seconds", "请求耗时（秒）", ["path"],
    buckets=(0.05, 0.1, 0.25, 0.5, 1, 2, 5),   # 分桶的边界，决定了精度
)


@app.get("/")
def index():
    """正常接口，很快返回"""
    with LATENCY.labels("/").time():        # 进入 with 时开始计时，退出时记录
        REQUESTS.labels("/", "200").inc()   # 计数 +1
    return {"msg": "ok"}


@app.get("/slow")
def slow():
    """慢接口，故意睡 0.1~1 秒，用来制造延迟故障"""
    with LATENCY.labels("/slow").time():
        time.sleep(random.uniform(0.1, 1.0))
        REQUESTS.labels("/slow", "200").inc()
    return {"msg": "slow"}


@app.get("/error")
def error():
    """错误接口，返回 500，用来制造错误率"""
    REQUESTS.labels("/error", "500").inc()
    return JSONResponse(status_code=500, content={"msg": "boom"})


@app.get("/metrics")
def metrics():
    """Prometheus 来抓数据时就访问这个路径"""
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)
```

**7. 跑起来**

```bash

```

- `app:app` = 文件 `app.py` 里的 `app` 对象
- `--host 0.0.0.0` = 允许外部访问（只写 127.0.0.1 的话外部连不上）
- `--port 8000` = 监听 8000 端口

> **注意**：D1 时服务是手动跑的。到了 D3 它会交给 systemd 托管（`aiops-app.service`），
> 那之后改代码一律用 `sudo systemctl restart aiops-app`，不要再用这个窗口手动起，
> 否则会和托管进程抢 8000 端口。

**这个窗口会一直占着**，先别关。


## D2 · 把数字画成图（Prometheus + Grafana）

> **📍 在哪做**
> - **环境**：虚拟机（SSH）
> - **目录**：`~/aiops`
> - **新建**：`prometheus.yml`、`docker-compose.yml`、`dashboards/`、`provisioning/`
> - **终端**：2 个（一个起容器、一个 curl 造流量）
> - **浏览器**：在 **Windows** 上开 `http://192.168.223.129:9090` 和 `:3000`

### 今天的目标

让 Prometheus 自动定时来抓你服务的数字，然后在 Grafana 上看到一个有曲线的面板。

### 为什么做这一步

D1 你只能 `curl` 看一眼**当下**的数字。但排障看的是**趋势**：

- 「CPU 现在 80%」——没关系，可能一直这样
- 「CPU 十分钟前 20%，现在 80%」——出事了

**没有历史数据，就没有判断依据。** Prometheus 就是那个「一直帮你记录」的东西。

### 用到的工具

| 工具 | 是什么 | 为什么是它 |
|---|---|---|
| **Prometheus** | 监控系统（时序数据库 + 抓取器） | 行业标准，K8s 生态默认用它 |
| **Grafana** | 可视化工具 | 图表好看，能设告警，支持各种数据源 |
| **Docker Compose** | 用一个文件描述多个容器 | 一条命令起两个服务，不用手动装 |

**关键原理：Prometheus 是「拉」不是「推」**

```
Prometheus 每 15 秒：  去访问 http://你服务:8000/metrics → 把数字存进自己的数据库
                        ↑ 这就是为什么 D1 要暴露 /metrics
```

它主动来「抓」（pull），你的服务被动等着。所以你的服务不需要知道 Prometheus 在哪。

**为什么要用 Docker 装它们**

Prometheus 是个 Go 程序，直接装要处理 systemd、用户、权限、版本……用 Docker 就是：

```bash
docker run prom/prometheus    # 完事
```

镜像里已经把环境打好了。

### 具体步骤

**1. 回到项目目录**

```bash
cd ~/aiops
```

**2. 写 Prometheus 配置**

```bash
vim prometheus.yml
```

```yaml
# prometheus.yml —— 告诉 Prometheus 抓谁、多久抓一次
global:
  scrape_interval: 15s        # 每 15 秒抓一次
  evaluation_interval: 15s    # 每 15 秒算一次告警规则（D4 才用）

scrape_configs:
  - job_name: "aiops-app"
    static_configs:
      # 注意：这里不能写 localhost！
      # 因为 Prometheus 跑在容器里，容器的 localhost 是容器自己
      - targets: ["host.docker.internal:8000"]
```

> **这是新手最大的坑**：容器内的 `localhost` ≠ 你的虚拟机。我们后面用 `extra_hosts` 把 `host.docker.internal` 映射到宿主机。

**3. 写 docker-compose.yml**

```bash
vim docker-compose.yml
```

```yaml
services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    ports:
      - "9090:9090"                      # 左边是虚拟机端口，右边是容器端口
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro   # 配置挂进去，:ro 表示只读
      - prom-data:/prometheus            # 数据存到命名卷，容器删了数据还在
    extra_hosts:
      - "host.docker.internal:host-gateway"   # 关键：让容器能访问宿主机
    restart: unless-stopped

  grafana:
    image: grafana/grafana:latest
    container_name: grafana
    ports:
      - "3000:3000"
    environment:
      GF_SECURITY_ADMIN_PASSWORD: admin  # 初始密码，登录后改
    volumes:
      - grafana-data:/var/lib/grafana
    restart: unless-stopped

volumes:
  prom-data:
  grafana-data:
```

**4. 启动**

```bash
docker compose up -d
```

`-d` = 后台运行。第一次会下载镜像（几百 MB），等一会儿。

**5. 看抓取是否成功**

浏览器打开 `http://192.168.223.129:9090`，点顶部菜单 **Status → Targets**。

应该看到 `aiops-app` 状态是 **UP**。

或者命令行验证：

```bash
curl -s localhost:9090/api/v1/targets | grep -o '"health":"[^"]*"'
```

**6. 配 Grafana 数据源**

1. 浏览器打开 `http://192.168.223.129:3000`
2. 登录：用户名 `admin`，密码 `admin`（会让你改密码）
3. 左侧菜单 → **Connections → Data sources → Add data source → Prometheus**
4. URL 填 `http://prometheus:9090`（**在容器网络里用容器名**，不是 localhost）
5. 拉到底点 **Save & test**，应该显示 `Successfully queried the Prometheus API`

**7. 建面板**

左侧 **Dashboards → New → New dashboard → Add visualization**，数据源选 Prometheus，然后依次加三个查询：

| 面板 | 查询语句 | 含义 |
|---|---|---|
| QPS | `sum(rate(app_requests_total[1m]))` | 每秒请求数 |
| P95 延迟 | `histogram_quantile(0.95, sum(rate(app_latency_seconds_bucket[1m])) by (le))` | 95% 请求快于多少秒 |
| 错误数 | `sum(rate(app_requests_total{status=~"5.."}[1m]))` | 5xx 每秒多少次 |

**看懂这两个函数**：

- `rate(x[1m])`：把「累计值」变成「每秒速率」。因为 Counter 只增不减，直接看总量没意义，要看增长速度
- `histogram_quantile(0.95, ...)`：从直方图里算出 P95。**为什么要 P95 不用平均值**？因为平均值会被少量极慢请求掩盖——100 个请求 99 个 10ms、1 个 5 秒，平均才 60ms，但用户体验是「有人卡了 5 秒」

> **如果面板编辑器报 `insertBefore` 错误**：这是 Grafana 前端的 bug，不是你配错了。
> 绕开办法是把仪表盘写成 JSON 文件让 Grafana 自动加载（provisioning），
> 仓库里的 `src/monitoring/` 就是这套做法的完整示例。

**8. 制造点流量**

```bash
for i in $(seq 1 50); do curl -s localhost:8000/ > /dev/null; curl -s localhost:8000/slow > /dev/null; done
```

刷新 Grafana，曲线应该动起来了。

### 你会看到什么

- `localhost:9090/targets` 里 `aiops-app` 是 **UP**，`Last Scrape` 显示几秒前
- Grafana 面板上有三条曲线，QPS 在你刷请求时出现尖峰
- P95 在 0.5~1 秒之间（因为 `/slow` 故意睡那么久）

### 卡住了看这里

| 现象 | 原因 | 解决 |
|---|---|---|
| Target 是 **DOWN** | Prometheus 连不上你的服务 | ① 确认 uvicorn 还在跑 ② `curl localhost:8000/metrics` 在虚拟机里能通 ③ 确认 compose 里有 `extra_hosts` |
| Grafana 数据源报错 | URL 写成了 `localhost:9090` | 改成 `http://prometheus:9090` |
| `docker compose` 报 command not found | 装的是旧版 compose | 试 `docker-compose up -d` |
| 拉镜像很慢 | 没配加速器 | 你装环境时已配好，检查 `/etc/docker/daemon.json` |
| 端口被占用 | 9090/3000 已被别的程序用 | `ss -tlnp \| grep 9090` |

### 做完检查

- [x] `docker compose ps` 显示两个容器都是 `Up`
- [x] Prometheus Targets 页面 `aiops-app` 为 UP
- [x] Grafana 能查到数据（数据源 test 通过）
- [x] 面板上有三条曲线，刷流量时能看到变化

## D3 · 让日志能「被查询」

> **📍 在哪做**
> - **环境**：虚拟机（SSH）
> - **目录**：`~/aiops`
> - **改**：`app.py`（只改这一个文件）
> - **自动生成**：`app.log`（不用手建，代码跑起来就有）
> - **终端**：2 个（一个看日志、一个造请求）

### 今天的目标

把服务的日志从「一行行普通文字」改成「每行一个 JSON」，然后用 `jq` 快速筛。

### 为什么做这一步

排障时你 80% 的时间在看日志。但普通日志长这样：

```
2026-11-10 16:30:01 INFO 请求 /slow 耗时 823ms from 192.168.223.1
```

你想「找出所有耗时超过 500ms 的请求」，只能 eyeball 或者写复杂正则。

改成 JSON 之后：

```
{"ts":"2026-11-10T16:30:01","level":"INFO","path":"/slow","latency_ms":823.4,"trace_id":"a1b2c3d4"}
```

一行命令就够了：

```bash
jq 'select(.latency_ms > 500)' app.log
```

**这是「可观测性」的核心思想：让机器能读懂你的日志。** 后面第 3 周，AI 分析故障时读的就是这种结构化日志——你给它一坨糊在一起的文字，它也没法用。

**trace_id 是什么**：一次请求的唯一编号。用户点一下按钮可能触发 5 个服务调用，有了 trace_id 就能把散落各处的日志串成一条线。

### 用到的工具

| 工具 | 是什么 | 为什么是它 |
|---|---|---|
| **logging**（Python 内置） | 日志库 | 不用装，标准做法 |
| **JSON 格式** | 一种数据格式 | 机器和人都能读，jq/程序都好处理 |
| **jq** | 命令行 JSON 处理器 | 一条命令筛字段，比 grep 精准 |

### 具体步骤

**1. 改造 app.py**

在文件开头加日志配置，然后加一个中间件。

```python
# 在 import 区加上
import logging
import json
import uuid
from starlette.middleware.base import BaseHTTPMiddleware

# ── 日志配置 ────────────────────────────────────────────
class JsonFormatter(logging.Formatter):
    """把日志格式化成一行 JSON"""
    def format(self, record):
        base = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"),
            "level": record.levelname,
            "msg": record.getMessage(),
        }
        # 把 extra 里传的自定义字段也带上
        for k in ("trace_id", "path", "status", "latency_ms", "client"):
            v = getattr(record, k, None)
            if v is not None:
                base[k] = v
        return json.dumps(base, ensure_ascii=False)

handler = logging.FileHandler("/home/shawny/aiops/app.log", encoding="utf-8")
handler.setFormatter(JsonFormatter())

log = logging.getLogger("app")
log.setLevel(logging.INFO)
log.addHandler(handler)
log.propagate = False      # 不要同时输出到屏幕，避免重复


# ── 访问日志中间件 ──────────────────────────────────────
class AccessLog(BaseHTTPMiddleware):
    """每个请求进出都记一条，自动带 trace_id 和耗时"""
    async def dispatch(self, request, call_next):
        if request.url.path == "/metrics":     # 抓指标太频繁，不记
            return await call_next(request)

        start = time.time()
        trace_id = request.headers.get("x-trace-id") or uuid.uuid4().hex[:8]
        response = await call_next(request)
        cost_ms = (time.time() - start) * 1000

        log.info("request", extra={
            "trace_id": trace_id,
            "path": request.url.path,
            "status": response.status_code,
            "latency_ms": round(cost_ms, 1),
            "client": request.client.host if request.client else "-",
        })
        response.headers["x-trace-id"] = trace_id   # 回传给调用方，方便串联
        return response

app.add_middleware(AccessLog)
```

> 注意：`app.add_middleware(AccessLog)` 要放在 `app = FastAPI(...)` 之后。

> - **新建 3 个文件**：`rules.yml`、`alertmanager.yml`、`receiver.py`

> - **终端**：3 个（① 跑 receiver  ② 造压测  ③ 看日志/状态）
> - **浏览器**：Windows 上开 `:9093` 看 Alertmanager
>
> **注意**：`receiver.py` 是前台进程，**不能用 systemd 那套管**，直接在终端里跑，`Ctrl+C` 停。

### 今天的目标

写一条规则：延迟超过 500ms 持续 1 分钟就报警。告警要能推到你自己的程序里，落成一行日志。

### 为什么做这一步

前三天你都是「人主动去看」。但故障发生在凌晨 3 点怎么办？

**告警 = 把「人盯屏幕」换成「机器盯屏幕，出事才叫你」。**

这一天的产物很关键：第 3 周的 AI 分析，**入口就是这个告警**。告警触发了，才去收集上下文，才让模型分析。

### 用到的工具

| 工具 | 是什么 | 为什么是它 |
|---|---|---|
| **Prometheus 告警规则** | 写在 yaml 里的 if-then 规则 | 直接复用已有的指标，不用另写代码 |
| **Alertmanager** | 告警路由器 | Prometheus 自己不负责发送，必须经过它；它还负责去重、分组、抑制 |
| **webhook** | 一个 HTTP 回调地址 | 告警发给你的程序，你爱怎么处理怎么处理 |

**关键原理：告警的三段链路**

```
Prometheus 每 15 秒算一次规则
        ↓ 超过阈值且持续 for 指定的时间
   产生一条告警（firing）
        ↓ 推给
   Alertmanager（负责分组、去重、决定发给谁）
        ↓ webhook POST
   你的程序（打印 / 存文件 / 后面接 AI 分析）
```

为什么要 Alertmanager？因为 Prometheus 只管「算」，不管「发」。而且真实环境里一次故障会产生几十条告警，Alertmanager 会把它们合并成一条，不然你会被淹死。

### 具体步骤

**1. 写告警规则**

```bash
vim rules.yml
```

```yaml
groups:
  - name: app-rules
    rules:
      # 规则 1：P95 延迟过高
      - alert: HighLatency
        expr: histogram_quantile(0.95, sum(rate(app_latency_seconds_bucket[1m])) by (le)) > 0.5
        for: 1m                    # 持续 1 分钟才报，避免抖动误报
        labels:
          severity: warning
        annotations:
          summary: "P95 延迟超过 500ms"
          description: "当前 P95 = {{ $value | printf \"%.3f\" }}s"

      # 规则 2：错误率过高
      - alert: HighErrorRate
        expr: |
          sum(rate(app_requests_total{status=~"5.."}[1m]))
          /
          sum(rate(app_requests_total[1m])) > 0.05
        for: 30s
        labels:
          severity: critical
        annotations:
          summary: "5xx 错误率超过 5%"

      # 规则 3：服务挂了（抓不到指标）
      - alert: AppDown
        expr: up{job="aiops-app"} == 0
        for: 15s
        labels:
          severity: critical
        annotations:
          summary: "应用无法抓取，可能已停止"
```

> `for` 是「持续多久才报」。没有它，一次网络抖动就会吵醒你。

**3. 写接收告警的程序**

```bash

```

```python
# receiver.py —— 接收 Alertmanager 推来的告警，存成一行行 JSON
import json
import datetime

from fastapi import FastAPI, Request

app = FastAPI(title="alert-receiver")
LOG = "/home/shawny/aiops/alerts.log"


@app.post("/alert")
async def receive(req: Request):
    body = await req.json()
    for a in body.get("alerts", []):
        line = {
            "time": datetime.datetime.now().isoformat(timespec="seconds"),
            "status": a.get("status"),                       # firing / resolved
            "name": a.get("labels", {}).get("alertname"),
            "severity": a.get("labels", {}).get("severity"),
            "summary": a.get("annotations", {}).get("summary"),
            "detail": a.get("annotations", {}).get("description"),
        }
        text = json.dumps(line, ensure_ascii=False)
        print(text, flush=True)                # 打印到屏幕
        with open(LOG, "a", encoding="utf-8") as f:
            f.write(text + "\n")               # 同时落盘
    return {"ok": True}
```

### 为什么做这一步

真实故障不可控、不可复现。但你可以自己造：CPU 打满、网络延迟、磁盘写满、进程杀掉。造完之后你才有「这个指标为什么会这样」的直觉。

### 用到的工具

| 工具 | 是什么 | 为什么是它 |
|---|---|---|
| **stress-ng** | 压力测试工具 | 一行命令把 CPU/内存/IO 打满 |

| **fallocate** | 快速分配磁盘空间 | 瞬间造出一个大文件，模拟磁盘满 |

**准备：先确认网卡名字**

**故障 2：网络延迟 200ms**

先理解一件事：**`tc` 只影响「从这块网卡出去」的包**。

| 你测的地址 | 内核走哪 | 加在 ens33 上有效吗 |
|---|---|---|
| `localhost:8000` | `lo`（回环） | ❌ 根本不走 ens33 |
| `192.168.223.129:8000`（本机 IP） | 也是 `lo`（内核内部回环） | ❌ 同上 |
| `curl https://mirrors.ustc.edu.cn` | `ens33`（真出网） | ✅ 有效 |

**这就是为什么在 ens33 上加延迟、测 localhost 却毫无反应。**

**方法 A：加在 lo 上（模拟本机延迟，最直观）**

```bash
sudo tc qdisc add dev lo root netem delay 200ms

# 应该从 0.01s 变成 0.21s
curl -w "耗时: %{time_total}s\n" -o /dev/null -s localhost:8000/

# 撤销（一定要撤销！）
sudo tc qdisc del dev lo root
```

**方法 B：加在 ens33 上，但测外网**

```bash
sudo tc qdisc add dev ens33 root netem delay 200ms
curl -w "耗时: %{time_total}s\n" -o /dev/null -s https://mirrors.ustc.edu.cn
sudo tc qdisc del dev ens33 root
```

**方法 C：从客户端方向限速**（在 Windows 上做，测 VM 的端口）

> **检查撤销干净了没有**：
> ```bash
> tc qdisc show dev lo       # 正常是 noqueue
> tc qdisc show dev ens33    # 正常是 fq_codel
> ```
> 看到 `netem` 就是没删。**留着不删，后面所有调试都会变慢，极容易误判。**

**故障 3：磁盘写满**

先算笔账：根分区 **36 GB**，写 2 GB 只占 **5.6%**，`df` 显示 6% 是**对的**。

```bash
df -h /                     # 看总量：36G
fallocate -l 2G /tmp/bigfile
df -h /                     # 14% → 20%，涨 6%
```

不是 `fallocate` 没生效，是**分母太大**。

**方法 A：直接写满根分区（不推荐）**

```bash
fallocate -l 28G /tmp/bigfile
df -h /                     # 接近 100%
rm -f /tmp/bigfile
```

> 根分区写满会连锁反应：systemd 起不来、日志写不进、SSH 可能异常。
> **别拿系统盘做这种实验。**

**方法 B：造一个小文件系统专门演示（推荐）**

```bash
# 1. 200MB 镜像
fallocate -l 200M /tmp/small.img
mkfs.ext4 -q /tmp/small.img

# 2. 挂载
sudo mkdir -p /mnt/small
sudo mount -o loop /tmp/small.img /mnt/small
df -h /mnt/small                        # 200M

# 3. 写满
sudo dd if=/dev/zero of=/mnt/small/fill bs=1M 2>&1 | tail -1
df -h /mnt/small                        # 100% ✅

# 4. 清理
sudo rm -f /mnt/small/fill
sudo umount /mnt/small
rm -f /tmp/small.img
```

好处：**几秒造出 100%，而且炸的不是系统盘**。真实运维里 `loop` 设备也常用来做隔离测试。

**故障 4：服务挂掉**

```bash
# 服务由 systemd 托管，正确停法：
sudo systemctl stop aiops-app

# 观察完再拉起来
sudo systemctl start aiops-app
```

> **不要用 `pkill`**：`Restart=always` 会让 systemd 在 3 秒内自动拉起，
> 这个故障根本造不成，你只会看到 PID 变了一下。

观察 Prometheus 里 `up{job="aiops-app"}` 变成 0，约 15 秒后触发 `AppDown` 告警。

> - **目录**：不依赖项目文件，随便在哪都行
> - **产物**：一页 cheat sheet，写进 `notes/D06-cheatsheet.md`
> - **终端**：1–2 个

### 今天的目标

掌握 4 个命令，覆盖「CPU / 网络 / 磁盘 / 服务日志」四类问题。

### 为什么做这一步

前面几天你在「造」故障，今天开始学「查」故障。

面试运维岗，80% 的技术问题都在这四个方向。**能不能说出「先看什么、为什么看这个」，就是你和别人的差距。**

### 用到的工具

| 命令 | 看什么 | 什么时候用 |
|---|---|---|
| **top** | CPU、内存、进程 | 「系统卡」的第一反应 |
| **ss** | 网络连接、端口 | 「连不上」「端口没起来」 |
| **iostat** | 磁盘 IO | 「慢」但 CPU 不高 |
| **journalctl** | systemd 服务日志 | 「服务起不来」 |

### 具体步骤

**1. top —— 先看整体**

```bash
top
```

按 `1` 展开每个 CPU 核，按 `Shift+P` 按 CPU 排序，`Shift+M` 按内存排序，`q` 退出。

**要看的三个数**：
- `%Cpu(s)` 那行的 `us`（用户态）、`sy`（内核态）、`wa`（等 IO）
- `load average`：1/5/15 分钟的平均负载，超过核数就是过载
- `%MEM`：哪个进程吃内存

> 你机器 2 核，load 超过 2 就该警觉。

**2. ss —— 看端口和连接**

```bash
ss -tlnp          # 监听中的 TCP 端口（l=listening, n=数字, p=进程）
ss -s             # 汇总统计
ss -tn state established | head   # 已建立的连接
```

**典型用法**：服务起不来，先确认端口有没有在听。

```bash
ss -tlnp | grep 8000
```

有输出 = 端口在听；没输出 = 服务根本没起来，或者监听在别的地址。

**3. iostat —— 看磁盘**

```bash
iostat -x 1 5     # 每 1 秒一次，共 5 次，-x 显示扩展信息
```

**要看的**：
- `%util`：磁盘有多忙，接近 100% 说明打满了
- `await`：平均等待毫秒数，超过 20ms 就偏慢
- `r/s` `w/s`：每秒读写次数

**典型场景**：用户说「系统慢」，但 top 里 CPU 只有 20%——大概率是磁盘 IO 卡住了，这时候 `wa` 会很高。

**4. journalctl —— 看服务日志**

```bash
journalctl -u docker --since "10 min ago"     # docker 服务最近 10 分钟日志
journalctl -xe                                 # 最近的错误
journalctl -u sshd -n 50                       # sshd 最后 50 行
```

**典型场景**：`systemctl start xxx` 失败，`journalctl -u xxx -n 30` 立刻能看到原因。

**5. 组合练习**

造一个 CPU 故障，然后只用命令行定位：

```bash
# 终端 A
stress-ng --cpu 2 --timeout 60s

# 终端 B：三步定位
top -b -n 1 | head -20            # 1. 确认 CPU 高，看是哪个进程
ps aux --sort=-%cpu | head -5     # 2. 找出吃 CPU 的进程
cat /proc/$(pgrep -f stress-ng | head -1)/cmdline   # 3. 看它到底是什么
```
