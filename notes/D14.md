## 二、踩的坑

### 1. 重跑评测把人工分弄丢了（`scored_answers: 0`）

D13 的 15 条 `score` 是**在宿主机上**加进 `eval/eval_result.json` 的，从来没同步回虚拟机。
所以 D14 在虚拟机重跑时，脚本读到的旧文件里没有 `score` 字段，`if "score" in old` 全部落空：

```json
{ "generation_ok": 20, "scored_answers": 0 }     // 分数一条没剩
```

更麻烦的是：**答案被重新生成了**。就算分数还在，也对不上新答案。

修法：把带分数的冻结结果 `scp` 回虚拟机，再用 `--reuse-answers-from eval_result.json` 跑后续口径复测，
保证「答案 + 分数」是同一次生成的。

教训：**人工打分必须落进仓库，不能只存在宿主机上**。凡是「人给的、脚本算不出来的」数据，
都要当成产物提交——否则下一次重跑就蒸发。

### 2. 答案均分从 2.0 下修到 1.933（我自己的评分偏宽）

D13 那轮 15 条我全给了 2 分（均分 2.0）。D14 重新按答案文本逐条独立评分时，第 6 题只值 **1 分**：

> 问：告警一直 firing，但接收端什么也没收到，先查什么？
> 答：「先检查阈值设置是否合理，或确认告警是否真的发生了问题。如果阈值合理且告警确实发生了，再检查 Alertmanager 和 Receiver 之间的通信是否正常。」

方向对（确实要查告警链路），但漏了两个**最关键的可执行动作**：
`ss -tlnp | grep 8001` 看 receiver 进程在不在、以及 Prometheus 重启后 `for` 计时归零要重新累计。
「先查什么」的题，答不出具体命令就是部分正确。

第 1 题也是类似情况（严格口径没命中 `D01.md`，但答案本身用了 Counter/Histogram 讲对了，给 2 分）。

**这是 0/1/2 评分最容易出问题的地方：第一遍打分容易「看懂了就给 2」。**
第二遍只看「有没有可执行步骤、有没有漏关键坑」，分数就会掉。冻结的时候应该用第二遍的口径。

### 3. `tar` 打包把 `monitoring/*.yml` 平铺到了根目录

D14 手册第 1 步给的打包命令是：

```bash
tar czf /tmp/aiops-code.tar.gz --exclude='.venv' --exclude='chroma' --exclude='corpus' \
    --exclude='__pycache__' --exclude='*.log' --exclude='.env' \
    *.py *.yml *.json docker-compose.yml
```

先澄清一个容易误判的点：**虚拟机的目录结构和仓库不一样**。
虚拟机 `~/aiops` 是**平铺的**，4 个 yml 直接躺在根目录（11-13 建的）：

```
alertmanager.yml  422B  docker-compose.yml 1268B  prometheus.yml 627B  rules.yml 1044B
monitoring/  <-- 目录根本不存在（ls monitoring/*.yml 无输出）
```

仓库里只有一个正本放在 `src/monitoring/`。所以打出来的包是：

```
app.py build_index.py ... run_eval.py search_test.py
alertmanager.yml docker-compose.yml prometheus.yml rules.yml
corpus_stats.json eval_result*.json eval_set*.json
docker-compose.yml                      <-- 出现了两次
```

两件事：

1. 命令本身有 bug：`*.yml` 已经包含 `docker-compose.yml`，末尾又显式写了一次，
   tar 列表里它出现两遍（`file changed as we read it` 的典型来源）。
2. 影响：如果直接 `tar -xzf ... -C src`，会在仓库 `src/` 根下多出 4 个 yml 副本，
   和 `src/monitoring/` 里的正本并存。**以后改配置改错文件都发现不了**。

修法：**不要整包解压**。D14 里 9 个 `.py` 的 md5 和仓库完全一致（见下），
根本不需要从包里取任何代码，逐个 `scp` 明确文件就够了：

```bash
scp root@192.168.223.129:/home/shawny/aiops/rag_service.py src/rag_service.py
md5sum src/rag_service.py    # 与虚拟机 md5 比对
```

### 4. 索引没有变，别被 `chroma/` 的 mtime 骗了

`ls -lt` 看到 `chroma/` 是 11-20 17:40，比 `corpus_stats.json`（11-19 16:49）新。
但那是**查询写的元数据**，不是重建：`corpus_stats.json` 仍是 `{"chunks": 179, "sources": 16}`。

判断有没有重建索引，只认 `corpus_stats.json` 的 mtime，不认 `chroma/` 目录。
