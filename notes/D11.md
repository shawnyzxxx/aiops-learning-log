## 二、踩的坑

1. **`KeyError: 'expected'`（手册里的原代码有 bug）**
   `eval_set.json` 的字段名是 `expected_source`，而手册 D11 示例代码第 686 行写的是 `if it["expected"] in sources:`。
   第一次跑直接崩：
   ```
   KeyError: 'expected'
   ```
   修法：`if it.get("expected_source") in sources:`（`rec["expected"]` 那行用 `it.get("expected_source")` 是对的，保留）。
   **已同步修正 handbook/W2-第2周.md 的示例代码**，避免下次照抄再踩。

2. **`eval_result.json` 属主是 root**
   root 通过 ssh 跑脚本写出的文件属主是 root，`shawny` 后续再跑会 permission denied。已 `chown shawny:shawny` 修正。
   以后固定在 `su - shawny -c` 下跑，或跑完 chown。

3. **`chroma/` 的 mtime 会骗人**
   `ls -lt` 看到 `chroma/` 是 16:13（今天），但 `corpus_stats.json` 还是 11-14——说明**没有重建索引**，
   只是查询时 Chroma 写了元数据。判断有没有重建，看 `corpus_stats.json` 的 mtime 才可靠。

4. **venv 没激活的老坑又差点踩**：开新 ssh 会话时提示符没有 `(.venv)`，`which python` 是 `/usr/bin/python`。
   养成习惯：**每次 ssh 进来先 `source .venv/bin/activate && which python`**。

## 三、为什么 0.867 远超预估的 0.5

手册预估 0.5 基于两个假设：语料覆盖稀、切分粒度粗。实际情况是：

- D10 把 5 条超纲题换成了语料真覆盖的主题（告警链路、trace_id、tc 延迟、端口占用、SRE 概念），
  15 条有答案题**全部落在 16 篇语料的语义范围内**；
- D8 切分是「按 `##` 标题层级切」，不是固定长度硬切，一个块基本等于一个完整知识点，
  bge-m3 对这种「一问一块」的匹配天然友好；
- 语料里 D01–D07 是本项目自己的复盘笔记，术语和问法高度重合。

所以 0.867 是**真实但偏乐观**的基线：它测的是「语料覆盖范围内的召回能力」，
不代表真实运维提问（大量超纲）也能到 0.87。这个边界要在 D14 写进 README，面试时也要讲清楚。
