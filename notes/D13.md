## 一、做了什么

### 1. `run_eval.py` 改成可复测、可对比的入口

原来脚本写死 `eval_set.json` / `eval_result.json`，改一次口径就得覆盖上一版数字。D13 加了三个参数：

| 参数 | 作用 |
|---|---|
| `--eval-file` | 指定评测集（默认 `eval_set.json`，向后兼容） |
| `--output` | 指定结果文件，历史数字不再被覆盖 |
| `--retrieval-only` | **只重算检索指标，不调聊天模型** |
| `--reuse-answers-from` | 按 `id` 复用旧结果里的 `answer` / `score` / `note` |

后两个参数是为了解决一个具体问题：**改评测口径只影响 recall，答案和人工分数一个字都不该变**。
之前每改一次口径就要重跑 20 次 LLM（几分钟 + 花 token），现在只要：

```bash
python run_eval.py --eval-file eval_set_d13.json \
    --output eval_result_d13.json \
    --retrieval-only --reuse-answers-from eval_result.json
```

同时 summary 里**两套口径都输出**，避免「同一份结果报两个数」的歧义：

| 字段 | 含义 |
|---|---|
| `strict_recall@5` / `strict_recall@10` | 只用 `expected_source` 单个文件判命中（D11/D12 的老口径） |
| `recall@5` / `recall@10` | 允许 `expected_sources` 里任一文件命中（D13 新口径） |

### 2. 评测集加「等价来源」但只加一条

新建 [eval/eval_set_d13.json](../eval/eval_set_d13.json)，**原始 `eval_set.json` 不动**（历史数字才能复现）：

```json
{ "id": 1, "expected_source": "D01.md", "expected_sources": ["D01.md", "basics.md"] }
```

不是 PromQL 写法，把 `api.md` 算作等价来源属于自己给自己送分。它继续按「严格未命中」计。

### 3. 新建 `rag_service.py`

```python
from rag import answer as _answer

def ask(question: str) -> dict:
    if not isinstance(question, str) or not question.strip():
        return {"answer": "", "citations": [], "confidence": 0.0,
                "ok": False, "error": "question must be a non-empty string"}
    try:
        result = _answer(question.strip())
        ok = bool(result.get("ok", False))
        return {
            "answer": result.get("answer", "") if ok else "",
            "citations": list(result.get("citations", [])) if ok else [],
            "confidence": float(result.get("confidence", 0.0)) if ok else 0.0,
            "ok": ok,
            **({} if ok else {"error": result.get("error", "generation failed")}),
        }
    except Exception as exc:
        return {"answer": "", "citations": [], "confidence": 0.0,
                "ok": False, "error": f"{type(exc).__name__}: {exc}"}
```

三个设计决定：

1. **不暴露 Chroma / BM25 / prompt**：第 3 周的告警闭环只调 `ask()`，换检索实现时不用改闭环代码。
2. **异常不往上抛**：告警链路里一次问答失败不能让整个分析流程崩掉，返回 `ok=False` + `error` 让调用方决定降级。
3. **四个字段永远存在**：调用方不用写 `if "answer" in r`。失败时 `answer` 是空串而不是 None，下游拼字符串不会炸。

## 二、踩的坑

### 1. 「语法正确但源码被吃掉一层反斜杠」→ EOL while scanning string literal

在宿主机上用嵌套 shell 写 `run_eval.py`，里面有一行 `print("\n=== 结果 ===")`。
经过「shell 引号 → heredoc → python」三层，反斜杠被吃掉一层，落到文件里变成：

```python
print("
=== 结果 ===")          # 字符串在换行处断掉
```

虚拟机 `python -m py_compile run_eval.py` 直接报
`SyntaxError: EOL while scanning string literal (run_eval.py, line 130)`。

修法：**干掉反斜杠本身**，用两次 `print` 换行：

```python
print()
print("=== 结果 ===")
```

教训：**跨层生成代码时，任何转义序列都是风险点**。能写脚本文件就别用 `python -c`；
必须带 `\n` 时，写完立刻 `py_compile` 一遍，不要等跑评测才发现。

### 2. 本地文件被改好了，改第二次反而报「找不到原文」

发现语法问题后先手工修了一版，隔一会儿又去「修同一处」，编辑工具报
`EDIT_CONFLICT: oldText was not found`。

原因不是工具坏了，是**第一次修已经生效**，第二次的 `oldText` 在文件里确实不存在了。
正确做法是**先读当前文件再决定改什么**，不要凭上一次的记忆重发编辑。

### 3. `--retrieval-only` 之前，改一次口径要重跑 20 次 LLM

第一次想验证等价来源口径时，直接 `python run_eval.py` 跑全流程：20 条题、每条一次 chat 调用，
两分多钟，而且**答案会被重新生成**——上一轮人工打的分对不上新答案，等于打分作废。

改成 `--retrieval-only --reuse-answers-from` 之后，同一件事只要十几秒（只算 embedding + BM25）。

## 三、关键发现：0.867 到底卡在哪

### 两条未命中，只有一条是检索的问题

| # | 问题 | 期望来源 | 向量排名 | BM25 排名 | 等价来源口径下 | 性质 |
|---|---|---|---|---|---|---|
| 1 | 请求次数/耗时用什么指标类型 | `D01.md` | top15 无 | top15 无 | ✅ `basics.md` 进 top5 | **评测集定义过窄** |
| 11 | PromQL 排除 4xx | `examples.md` | 第 9 | 第 8 | ❌ 仍只进 top10 | **真·检索未命中** |

第 1 题：语料里 `D01.md` 的 192 字小块写「Counter 和 Histogram 的区别」，
题目问「请求次数和请求耗时」——同一件事两种说法。`basics.md` 把这几个指标类型讲得更完整，
所以它答对同一问题完全合法，**允许它命中不是放水，是修正评测集的错误**。

第 11 题：`examples.md` 在两路检索里都排 8~9 名，融合后进 top10、进不了 top5。
这是**真的差一口气**，靠换检索方法没解决。要真提上去只有两条路：
语料侧给 PromQL 例子单独成篇，或查询侧做改写（把「排除 4xx」映射到 `!=~"4.."` 的写法）。
两条都是第 3 周以后的事，D13 不做。

### 所以「recall@5 一直是 0.867，我感觉没什么好改的」对不对

**对了一半。** 对的部分：检索方法继续调（换 embedding、调 top-k、加 reranker）在这份语料上收益极小，
13/15 是稳定命中，剩下 2 条一条是评测集问题、一条是语料覆盖问题，**都不是检索算法能修的**。
错的部分：0.867 不是「天花板」，是「口径」——把第 1 题按合法等价来源算进去就是 0.933。

面试时正确的说法是：

> recall@5 = 0.93（15 题里 14 题的答案来源进了前 5），严格单来源口径是 0.87；
> 两条未命中我逐条定位过：一条是我评测集把「合法等价来源」排除了，改口径后命中；
> 另一条是语料里没有 PromQL 排除写法的例子，需要补语料而不是调检索。

**比报一个更高的数字值钱得多**——因为它证明你知道数字为什么是这个数字。

### 答案均分的口径要说清楚

`answer_avg_score = 2.0`（15 条全 2 分、共 30 分）是**按 0/1/2 三档打的人工分**，
但这一轮的打分是**在已看过检索命中情况的前提下做的**，不是盲评。
写进简历时要写「按 0/1/2 标准人工评分，平均 2.0/2.0（15 条）」，
不要说成「准确率 100%」——**recall 是检索命中率，不是答案正确率，两个数不能互换**。
